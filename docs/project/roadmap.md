# 实施阶段与任务拆解

状态：本分支的单次战斗与整局框架候选已实现，待团队认可。日期：2026-11-16。已有 Python 原始账号、角色与遗器生成，以及 Rust 基础战斗和离线同场批量评估；本轮增加单次战斗到整局结算的框架基础。具体测试结果以本分支交付记录为准。

本计划使用 F0—F5 编号。先提交框架候选并取得团队反馈，再按认可的范围扩展规则、完整对局、决策和训练。旧 M0—M5 的对应关系见文末迁移表。目标见[项目目标与使用方式](overview.md)，接口含义见[系统设计与技术方案](architecture.md)。

## 已确定方向与阶段依赖

已确定的主线是：对一场战斗尝试采样一次，保存成功或失败结果，按实际结果结算生命与经济，再推进到下一个局面。训练采集多条独立完整对局；同场批量胜率用于候选比较和离线评估。核心采用 Rust，玩家端采用 Tauri + TypeScript，已有 Python 账号生成继续保留。

Python/PyO3 训练绑定、根 Cargo workspace 与组合 wheel 属于待评审的工程方案。训练算法、奖励、模型规模及真实结算规则需要各自的证据与验收。Rust 和客户端方向已选定，不再列为待选语言；待确认的是具体接口、支持范围与接入顺序。

| 阶段 | 目标 | 开始条件 |
| --- | --- | --- |
| F0 | 完成单次战斗与整局框架候选，提交 PR 请求团队认可 | 本轮执行 |
| F1 | 核实选定范围的游戏规则，接入账号生效配置与机制 | F0 获认可，或明确满足有条件认可的前置要求 |
| F2 | 将已验证节点、经济与资源连接为独立完整对局 | F1 对应规则与输入已验收 |
| F3 | 接入合法候选、运营与战斗建议及离线比较 | 所需 F1/F2 环境能力已验收 |
| F4 | 接入训练绑定、独立轨迹采样和账号适配学习 | 环境、观测、动作与奖励方案已验收 |
| F5 | 交付 Windows 玩家预览版 | 所需核心与建议接口稳定，接入范围获确认 |

F1 之后可在接口明确后安排相互独立的任务，但完整角色扩展和训练均须先经过 F0。表中后续阶段表示计划，当前分支不自动进入这些工作。

## F0：框架实现与团队认可门

当前先把一条真实采样的模拟轨迹连接起来。公开样例使用合成战斗输入与结算规则，展示“节点败局后仍存活 → 下一节点胜利 → 整局完成”，并保留失败经历。该流程验证模块连接与状态变化；游戏内扣血、奖励与全部角色机制在 F1 单独核对。

| 编号 | 本轮任务与交付物 | 验收重点 |
| --- | --- | --- |
| F0.1 | 重构项目目标、架构、路线及模块入口 | 主线、已有能力、待认可接口和后续范围一致 |
| F0.2 | 在 `core/run` 接入 `core/battle` 的单次调用 | 一次尝试调用一次真实战斗核心，记录原结果和 AV 诊断 |
| F0.3 | 建立待结算状态、显式版本化规则与结算回执 | 按实际胜败平结算；缺规则保留同一结果，补规则后无需重新采样 |
| F0.4 | 实现当前生命、金币、晶矿和节点更新；独立保存固定生命上限 | 变更原子提交；旧修订、错节点和重复请求不会二次增减资源 |
| F0.5 | 提供可见观测与实际转移记录 | 种子、未来场景和完整回放不进入策略观测；失败保留，未知奖励不填默认值 |
| F0.6 | 提供公开合成 CLI、端到端与边界用例 | 覆盖多节点、生命归零、待结算、取消、动作上限、余额越界、隔离与复现 |
| F0.7 | 完成检查、证据整理与发布前独立评审 | 保留既有 battle 回归，记录实际执行的测试、格式、Clippy、rustdoc、release 和文档检查 |
| F0.8 | 提交框架 PR 并请求明确认可 | PR 列出以下认可清单；发布后停止扩展，等待团队反馈 |

本分支已提供框架候选；运行检查的命令、结果与局限随交付记录提供。检查通过可以证明相应软件行为，不能替代团队对职责和接口的认可，也不能证明合成规则符合真实游戏。

### PR 需要团队逐项确认什么

| 认可项 | 本分支提出的具体约定 |
| --- | --- |
| 主调用与评估边界 | 当前轨迹按一次战果推进；同场多种子 batch 留作候选比较和离线评估 |
| 单场结果 | 返回原胜负与可验证终止原因；自然 AV、罚时、非负剩余 AV、有符号余量与超支分列 |
| 状态所有权 | battle 维护战斗内状态，run 维护整局生命、经济、节点和结算；策略提出操作 |
| 结算与阻塞 | 显式规则按实际结果结算一次；缺规则保存待结算结果，未完成计算不当正常败局结算 |
| 版本与重试 | 对局、节点、尝试、修订号和版本可追溯；重复请求幂等，真实重试语义按规则证据接入 |
| 观测与训练记录 | 策略只见可见状态，复现信息另存；失败轨迹保留，奖励未定义时为未知 |
| 账号与规则接入 | 原始账号生成保留，生效配置供战斗和模型共用；真实规则需明确来源与支持范围 |
| 技术连接与分工 | Rust 核心和 Tauri + TypeScript 方向已定；Python/PyO3、构建布局、配置转换归属及下一阶段分工需评审 |
| 下一阶段范围 | 确定 F1 首个游戏版本、节点、角色机制、输入资料与验收记录 |

请团队给出“认可”“有条件认可”或“不认可”，并逐项说明阻塞问题、需修改内容和接受条件。有条件认可时先落实条件，再确认允许进入的任务范围；不认可时先修订对应框架。PR 发布后等待明确反馈，认可结果与合并状态分别记录，后续开发按已确认范围安排。

本轮范围不包含完整商店和投资、真实账号最终面板、全角色触发器、Cycle 规则重写、训练算法、Python 绑定或 Tauri 界面。

## 任务对接与交付

每项任务写明编号、依赖、当前输入、实施步骤、交付物和完成判断。接口明确后可并行开发，同一状态与规则由所属模块维护；实际模块联调结果另行记录。

例如，开始 F1.1 时，先选一场能再次进入或有完整记录的战斗，固定版本、节点、双方配置、操作方式和一个可核对问题，再整理初始状态、事件顺序、观测与缺项。F1.4 按这些记录验证，不用当前引擎输出反过来生成预期答案。

开始 F3.2 时，先固定一个节点的可见状态和资源约束，列出合法操作及拒绝样例；为每个候选保存操作对象、参数和前提，再交给环境副本执行。候选生成与收益评估分别验证。

交付至少包括目标仓库、分支与提交版本、输入与规则版本、运行命令、实际检查结果、未覆盖项和阻塞依赖。PR 关联未合并依赖，并说明本轮请求的决定。协作流程见[Git 协作规范](../development/git-workflow.md)，检查要求见[开发与测试约定](../development/development-guide.md)。

模拟与真实对局分别报告结果、样本量和局限。软件测试、合成规则示例、真实游戏规则核对和策略效果各自给出证据；状态文字随实际交付更新。
