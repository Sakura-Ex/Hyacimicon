# 项目目标与使用方式

状态：本分支的单次战斗与整局框架候选已实现，待团队认可。日期：2026-11-16。已有原始账号生成、基础战斗核心及同场批量评估；本轮在 `core/run` 接入单次战斗、结果结算与轨迹记录。具体运行检查以本分支交付记录为准，框架能力与完整游戏适配分别验收。

## 项目目标

本项目开发面向 Windows 玩家的开源货币战争策略工具。工具根据玩家的账号资源和当前局面，比较阵容、战斗操作和运营方案，为一整局游戏提供建议。玩家查看建议后，在游戏中执行操作。

核心目标是在给定时间内，提高最高难度下的整局通关概率，并帮助玩家连续多局通关（局外连胜）。这里的时间指玩家完成整局所花的总时间，包括操作、重试和等待计算；重叠时间只计一次。具体时间预算与通关判定在选定验收场景时固定。

生成建议时需要考虑账号可用资源、当前可见信息、随机发牌、节点进度和操作时间。研究阶段可以探索各种合法配置；面向玩家的建议应符合该账号实际可用的资源及合法试用配置。

普通对局以整局通关结果评估。研究还将训练模型适应不同账号，并运用多种阵容及运营路线，各类打法分别报告效果。伤害、血量、金币、晶矿和局内连胜用于分析局面及辅助训练；训练奖励与任务成功条件对应，尚未定义的奖励保留为未知。

挑战任务可以组合全试用、SSS、不重开和连续多局使用不同打法等条件。当前讨论的目标为连续 20 局、全试用、每局最终血量至少 100，且打法不同。SSS 在该挑战中按最终血量 ≥100 判断，当前血量与血量上限分别记录。最高伤害角色不同，或决定性因素不同，都可以作为打法差异的依据。具体伤害统计范围、决定性因素判定、整局重开与战斗重试限制，在挑战开始前固定。挑战效果以整套任务完成率评估。

## 一条对局怎样推进

模拟的主线是一条实际采样的整局轨迹。对当前节点选定的一次战斗尝试，环境调用战斗核心一次，记录该次结果；再按适用规则结算生命、经济和节点进度，继续到下一决策点。某场败局若未使整局结束，仍保留其损失与后续局面，成为这条轨迹的一部分。

单场结果报告胜负、可验证的终止原因和 AV 使用情况。AV 是战斗中的行动值时间，与玩家操作耗时和计算耗时分开记录。结果同时保留自然经过 AV、复活罚时、非负剩余 AV 和有符号余量，供调用方识别是否超支。终止原因说明这一场怎样结束；阵容不足或策略失误等因果判断需要额外分析。

战斗结束与整局资源结算是两个步骤。结算规则缺失时，环境保存已采样结果，等待补齐规则后继续结算，避免重新抽取战果。取消、动作上限等造成的未完成计算单独记录，不能作为正常败局扣血或生成普通败局经验。

训练时运行多条相互独立的整局轨迹，每条轨迹保留实际成功与失败经历。同一场景的多种子胜率统计继续用于候选比较、规则检查和离线评估；当前轨迹依据自身这一次结果推进，统计均值留在评估记录中。

## 玩家使用流程

计划中的使用流程如下：

1. 在本地录入或导入账号资源和当前局面。
2. 查看推荐操作、备选方案、推荐理由和评估范围。
3. 在游戏中执行操作，并反馈实际结果。
4. 依据实际结果更新局面，在下一个决策点继续获取建议。

候选试算使用独立副本，玩家当前局面的资源依据实际反馈更新。研究端的模拟轨迹与玩家实局记录分别保存。

玩家端采用 Tauri + TypeScript，计划提供 Windows 安装包，在本地离线运行，使用 CPU 完成规则计算、轻量模型推理和限定时间内的方案搜索。最低硬件配置与响应时间通过原型实测确定，测试时同时运行游戏。

账号导出首轮接入 [reliquary-archiver](https://github.com/IceDynamix/reliquary-archiver) 的 JSON，根据实际样本核对字段和角色标识。账号导出、程序生成和试用数据经过统一转换，按货币战争规则得到实际生效配置，再分别生成模型输入与战斗输入。配置表示、生成与评价方法见[账号与遗器数据](../modules/account-generation/design.md)。

## 研究设备与技术安排

研究端负责独立整局采样、离线候选评估、搜索和模型训练，为玩家端提供策略与模型。开发主机配置为 i9-14900K、RTX 4090、96 GB 内存，约有 3 TB 可用磁盘。

规则与模拟核心采用 Rust；已有 Python 账号生成继续使用。研究端通过共用核心开展训练的方向已提出，Python/PyO3 绑定及其打包接口仍待评审与接入。框架记录训练所需的转移，不代表训练器、并行采样调度或模型已完成。模块边界和技术状态见[系统设计与技术方案](architecture.md)。
