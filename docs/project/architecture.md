本章说明模块职责、一次战斗如何推进整局，以及玩家建议与训练如何复用环境。目标见[项目目标与使用方式](overview.md)，认可清单和实施顺序见[实施阶段与任务拆解](roadmap.md)。

## 模块职责

系统围绕完整对局组织。战斗核心计算一场战斗，整局环境维护节点与资源，策略从当前可见信息中选择操作。

| 模块 | 职责与状态归属 | 当前接入状态 |
| --- | --- | --- |
| 战斗核心 `core/battle` | 推进战斗内的行动、伤害、资源和事件，返回本次战斗结果 | 已有 `basic_v1`、单次模拟与同场批量评估，支持范围见模块说明 |
| 整局环境 `core/run` | 维护整局生命、经济、节点、修订号与待结算结果；调用战斗并结算一次 | 本分支实现框架基础，结算示例使用合成规则 |
| 账号生成器 | 生成角色、光锥与遗器原始配置，保留参数、资源指标与随机种子 | 已有 Python 实现 |
| 账号适配与配置转换 | 统一来源、字段和单位，按游戏版本得到生效配置与可用资源 | 待接入，模型编码和战斗组装共用输出 |
| 战斗规划器 | 在给定配置和约束内比较站位、操作、自动战斗与重试方案 | 待接入，通过环境副本评估 |
| 运营决策器 | 比较买卖、升级、储蓄、投资、过渡与转型方案 | 待接入，从环境取得观测和合法操作 |
| 阵容研究与实验评估 | 比较候选、采集独立整局、回放并分析模拟与实局差异 | 已有单场离线评估基础，完整流程待接入 |
| 训练适配与训练器 | 将环境观测、操作和实际转移交给学习算法 | 仅有框架记录基础，绑定与训练器待评审、实现 |
| 玩家应用 | 导入局面，展示建议、进度与理由，接收实际反馈 | Tauri + TypeScript 方向已选定，界面待实现 |

[战斗核心](../../core/battle/README.md)和[整局框架](../../core/run/README.md)维护各自的实际 API 与运行方式。完整商店、投资、角色触发器和真实账号最终面板仍需逐项接入；框架中可表达这些数据，不等于已经覆盖对应游戏规则。

## 一次战斗与整局推进

### 单次采样是主调用

一次战斗尝试的主流程如下：

1. 整局环境检查当前节点、状态修订号、操作身份和版本，接收已校验的战斗输入。
2. 对该尝试调用一次 `battle::simulate_cancellable`，保存本次结果及复现信息。
3. 对已完成的战斗，按实际 `Outcome` 选择适用的胜、败或平局结算规则。
4. 环境校验全部资源变更，原子更新生命、经济和节点，生成结算回执及前后观测。
5. 若整局仍可继续，进入下一决策点；达到结束条件时记录整局结果。

当前轨迹的一次尝试不会先运行一批同场模拟再抽选战果。批量评估可在独立副本中比较候选，其胜率、平均余量和期望资源变化作为评估结果返回。选定方案后的轨迹使用自身的单次战果结算。

同一局中，战斗败局与整局失败分别记录。某节点败局结算后仍有生命且规则允许继续时，推进到下一节点；生命耗尽或达到其他明确的整局结束条件时才结束整局。节点结束、节点胜负和整局状态使用各自的字段。

### AV 与失败原因

AV 表示战斗内的行动值时间。本轮沿用战斗核心对终止与行动的既有规则，整局层从原结果计算诊断：

| 指标 | 口径 |
| --- | --- |
| `max_av` | 本次战斗输入的 AV 预算 |
| `elapsed_av` | 原战斗结果中的自然经过 AV |
| `penalty_av` | 原战斗结果中的累计罚时，与自然经过 AV 分列 |
| 有符号余量 | `max_av - (elapsed_av + penalty_av)` |
| `remaining_av` | `max(0, max_av - (elapsed_av + penalty_av))` |
| 超支量 | `max(0, -有符号余量)` |

战斗核心可能在一个已完成动作中同时产生消灭敌方和罚时。结果是否胜利沿用核心的终止优先级；整局层保留有符号余量和超支信息，不能仅凭余量小于零重新判负。AV、计算耗时和玩家实际耗时分别计量。

失败说明直接引用已记录的终止原因及可验证统计。例如，预算耗尽可以解释此次计算如何结束；“阵容太弱”“运营错误”属于另行验证的策略分析。输入无效、机制不支持、取消或计算异常单独报告。

### 待结算、幂等与原子更新

战斗已完成而适用结算规则缺失时，环境保存同一份战果，状态停在待结算。补齐规则后从该结果继续结算，随机结果保持不变。调用方可以看到战斗完成与结算未完成这两个事实。

结算请求关联对局、节点、尝试、状态修订号和所用版本。环境拒绝错节点、过期修订和冲突请求；重复提交已结算的同一尝试，返回既有回执或明确拒绝，资源只能变化一次。每次结算先检查全部变更是否合法，再统一提交；任一余额或参数校验失败时保留原状态，不能只更新其中一项。

整局生命、生命上限、金币和晶矿独立存储。结算规则显式携带规则版本、标识和来源说明，通过节点配置或结算请求关联当前节点；首版仅接受合成规则，没有额外的真实节点适用性推断。正式游戏的扣血、奖励、连胜、利息与节点推进规则需另行核实和接入，缺值不以默认常数代替。

`Incomplete` 表示这次计算尚未得到可结算战果，例如被取消或达到动作上限。它不触发正常胜负资源结算，不生成普通败局训练转移。已有完整战果、待结算结果、未完成计算和非法请求需要让调用方区分。

## 共用数据与状态管理

### 账号、生效配置与版本

账号导出和程序生成先提供原始持有配置。配置转换按角色 ID、版本规则和合法试用约束补齐资源，得到实际生效配置与可用资源，再供模型输入编码和战斗输入组装共用。阵容选择与装备分配由策略提出，环境检查资源约束。

[账号与遗器数据](../modules/account-generation/design.md)维护原始字段、生成规则、资源评价和样例。本轮战斗仍接收显式有效面板，账号生成到完整战斗配置的自动转换属于后续任务。

跨模块记录关联对局、节点、尝试或操作、状态修订号、规则版本、账号配置版本与场景版本。输入、结算回执和轨迹应能相互追溯。规则缺失、来源不明及未支持机制显式返回；具体游戏规则及核实状态见[游戏规则](game-rules.md)。

### 内部状态、策略观测与玩家反馈

整局环境拥有完整内部状态。给策略的 `Observation` 只包含当前可见状态；当前 `Ready` 状态只提供 `FightCurrentNode`，其他状态不提供策略动作；后续扩展运营和战斗准备操作时也遵守同一可见性边界。未来场景、随机种子、隐藏状态与完整回放保留在环境内部或复现记录中。

同一局在每次合法操作后继续演进；不同对局和候选副本各自拥有状态与随机源。更改一个环境的生命、余额或节点不能影响另一个环境。训练所需的并行调度器尚待实现，本轮先提供环境隔离基础。

模拟状态与玩家实局记录分别维护。建议试算只推进副本，玩家当前局面的资源依据实际观测和反馈更新。反馈采用事件标识去重，并核对原状态版本；更新局面后，旧建议需重新检查。真实游戏的重试与重进随机规则仍按验证证据接入，模拟种子的复现能力不代替这项验证。

### 随机源与训练转移

模拟显式传入随机种子并记录版本，便于复现本次战斗。完整训练采样器还需管理各对局、节点和尝试的随机源分配，确保独立对局互不共享可变环境，也不会因补结算而重新采样。玩家重试语义由相应游戏规则约束。

训练记录保存前后可见观测、操作身份、实际战果、资源变化、结束状态，以及规则、账号、场景版本和种子。复现记录可以包含种子，提供给策略的观测不包含种子。奖励尚未定义时记录为未知，由后续奖励方案显式补充。

实际败局与其后续状态属于正常经验，应保留在所在整局中。未完成计算、输入拒绝和程序异常另存诊断。一次转移的资源变化来自实际结算，不能将多次模拟的平均收益或胜率写成该次经历。

## 运营决策与候选评估

运营决策器从合法动作中生成购买、升级、储蓄或换阵容等方案，在环境副本上比较。需要判断战斗影响时，调用战斗规划器，并传入该方案的配置、可见状态和剩余计算预算。战斗规划器返回结果，运营决策器结合后续经济和整局目标选择建议。

战斗规划器比较给定范围内的站位、技能操作、自动战斗或重试方案。它通过环境取得合法输入并调用战斗评估；涉及金币、节点收益和整局进度的变化始终由整局环境执行。

候选可先快速筛选，再对少量方案进行详细模拟；同场多种子批量模拟用于衡量随机性。所有这些结果标明局部或整局范围、样本量与假设。最终单条模拟轨迹按选中的操作继续推进，玩家应用则等待真实反馈更新实局。

未来的一次玩家建议请求按以下顺序完成：

1. 导入资源和局面，建立带版本的请求；关键输入不足时返回具体缺项。
2. 取得当前观测、合法操作和计算预算，选择运营或战斗决策模块。
3. 在独立副本中评估候选，共用本次请求的截止时间和取消信号。
4. 返回合法推荐、备选、理由、适用前提与评估范围；统计结论附样本量。
5. 玩家应用核对版本后展示建议，接收玩家手动执行后的实际结果。
6. 环境校验反馈、更新局面并记录，下一决策点再发起请求。

该建议入口、完整合法动作集合和玩家界面属于后续接入范围。

## 时间预算与执行状态

战斗 AV 预算决定游戏模拟中的时间边界；动作数量限制和取消信号控制计算；玩家整局时间预算约束策略使用成本。这些预算分别记录和解释。

本轮单次调用传递取消信号，并保留原战斗的完成状态。后续搜索和批量研究需提供任务标识、进度、共同截止时间和取消入口，结束时返回已完成且合法的候选，并说明未完成范围。尚无可用结果时返回原因。

玩家界面展示前检查请求标识与状态版本。统计时区分正常游戏胜负、计算未完成和输入问题。玩家总耗时包括操作、重试和等待计算，按实际经过时间统计，重叠只计一次；研究端离线采样与训练耗时另记。

## 运营模型与训练

### 训练单位与候选模型

训练以多条独立整局轨迹为基本单位。每条轨迹持续选择操作、采样战斗、结算并进入下一状态，直到整局结束；失败经历与成功经历一并保留。连续挑战再将多局组织为完整任务，并记录前面已使用的打法和剩余条件。

模型实验拟从稠密 Transformer 开始。角色、光锥、遗器、羁绊等实体与当前局面、资源和任务条件共同编码，站位与装备归属显式表示。策略头为合法操作评分，价值头估计当前任务条件下的后续成功可能性。

可比较约 500 万、2000 万和 5000 万参数的模型，固定独立整局数量、训练时间及推理搜索预算，记录 CPU 耗时与资源占用。这些是待验证的实验范围；模型结构与参数量由原型结果确定。

### 探索与训练阶段

环境与数据接口通过认可和验收后，再开展强化学习。PPO 为候选算法，首轮可从随机策略探索；搜索结果和优秀轨迹可供独立的模仿学习步骤使用。PPO 更新采用相应策略采集的数据，数据来源分别记录。

| 阶段 | 练习内容 | 评估重点 |
| --- | --- | --- |
| 基础运营 | 较短流程中的买卖、升级、刷新、投资和阵容调整 | 与随机及规则策略比较跨节点收益 |
| 完整对局 | 从开局到结算，练习过渡、资源分配和转阵 | 独立对局的通关结果、失败位置与资源轨迹 |
| 多种打法 | 指定或随机核心角色、羁绊和装备条件 | 各类打法及未见组合的表现 |
| 全试用 SSS | 使用已核实试用配置练习保血和困难节点 | 分打法统计最终血量、SSS 率与失败原因 |
| 连续挑战 | 从连续 3、5 局逐步增加到 20 局 | 整套完成率、重开约束、打法差异与剩余选择 |

不同账号和打法从早期加入，持续混合高、中、低配置，并保留固定测试集。辅助奖励另行定义、验证；局部伤害或胜率不能代替整局成功条件。

### 打法档案与挑战约束

优秀打法档案保存阵容、账号条件、过渡路线、装备分配、操作轨迹和独立评估结果。候选经评估后进入档案，训练从不同类别采样。MAP-Elites 可作为维护多类候选的方法。

打法差异按[挑战目标](overview.md)中的最高伤害角色或决定性因素判断，分类与对照方法在评估前固定。核心羁绊、投资、装备与辅助作用可通过合法替换对照分析。连续挑战观测增加已完成局数、已用打法和剩余条件，SSS 按任务约定的最终血量判断，生命与上限分别输入。

## 策略研究与评估

候选比较可以采用规则策略、Beam Search、MCTS、MAP-Elites、模仿学习或强化学习。各方法使用同一套环境规则和资源约束，分别记录效果与成本。

实验记录代码、规则、账号、场景与策略版本，随机源、结果和耗时。同场批量评估报告其场景、样本量和统计口径；整局评估报告完整轨迹数量与结束原因。两者的统计单位分别保留。

数据按账号生效配置、整局和完整挑战分组，同一局及同一挑战不跨训练与测试集合。映射到同一生效配置的不同来源按同组处理。完成调参后，在未参与训练或调参的账号、场景和组合上评估。

模拟与真实对局分别报告通关率、SSS 率、整套挑战完成率、样本量和耗时，并按账号资源与打法分组。失败案例和模拟误差保留复现信息。任务有时间预算时，预算内达标率以全部有效评估样本为分母，超时保留在分母，最终对局结果另记；输入缺失和计算异常单列。
