# 装备效果 JSON 结构与机制覆盖方案

状态：设计草案，2026-11-18。本文只设计文件格式、准备步骤和机制范围；相关装备读取、转换及执行扩展尚未实现。

本次按[遗器套装效果](../../game-data/relic-set-effects.md)中的 64 套、98 条套装效果，以及[光锥效果](../../game-data/light-cone-effects.md)中的 172 件光锥检查机制需求。资料适用 4.7，固定配置提交为 `dfdfe3337bcfa14f000074d2dae7058118193ea6`；这些表已核对配置文本与参数，游戏内及货币战争适用情况仍按表中状态核对。

当前代码对照版本为 `e961560`。本文按机制给出代表条目与缺口，不将条目计数换算成已支持装备数量。装备输入的职责、来源与实例设计见[装备效果与 Buff 生命周期](equipment-effects.md)。

## 三种数据分别表达什么

| 数据 | 内容 | 谁处理 |
| --- | --- | --- |
| 装备效果模板 | 装备 ID、参数五档、规则、状态定义、资料来源 | JSON 文件维护 |
| 本场装备绑定 | 穿戴者、具体装备或模板来源、叠影等级或套装件数 | 调用方在开战前传入 |
| 准备后的效果定义 | 参数全部取值完成、来源明确、能力检查通过的规则 | Rust 准备步骤生成，战斗执行器消费 |

JSON 保留五档叠影参数。准备步骤按本场叠影取值，也可以为同一模板导出五份固定参数的定义；运行时只安装选中的一份。一个光锥的多个被动会展开成多条规则和状态，不预设为一个 buff。

叠影 1～5 共用 Rust 类型与通用机制。五份数值定义按 `装备 ID + 叠影 + 规则版本` 区分，buff 共存组使用单独的稳定标识。这样不同叠影的同类效果仍按同类效果的共存规则处理。

模板中的变量必须引用显式参数、效果局部变量或可见战斗状态。算术使用表达式节点表示，字符串保留给 ID 和枚举值。

## 静态效果与战斗效果

按[账号静态面板约定](../account/playable-configuration.md)区分计算归属。`account` 已在转换中汇总已激活小行迹、遗器主副词条、达到件数门槛的套装无条件常驻属性，以及命途匹配光锥对应叠影的无条件常驻属性。

JSON 将两部分显式分组：

- `static_effects`：引用 `account` 已有的装备静态属性资料。引用根据根节点的装备种类、ID、资料版本与本场绑定解析；静态数值继续在现有资料中维护，按件数或叠影由 `account` 计算。
- `battle_effects`：保存本场战斗使用的参数、状态定义与规则，包括事件触发、当前目标条件、实时属性门槛和团队光环。

静态与战斗的划分按计算规则决定；持续时间使用另一组字段表达。永久战斗 buff、仅开战时判断一次的条件效果都归战斗侧。例如「齐颂」开战后给予我方全体攻击加成，即使没有回合倒计时，也由战斗处理。

| 装备 | 静态效果，由 account 计入面板 | 战斗效果，由 battle 处理 |
| --- | --- | --- |
| 快枪手 `102` | 二件攻击提高 12%；四件速度提高 6% | 四件普攻伤害提高 10% |
| 无可取代的东西 `23002`，叠影 1 | 攻击提高 24% | 击杀或受击后的治疗、增伤、次数与持续时间 |
| 秘密誓心 `21012`，叠影 1 | 无条件伤害提高 20% | 按当前敌我生命比例判断的额外增伤 20% |

`static_effects` 在装备文件中作为关联与核对信息，战斗执行器安装 `battle_effects`。准备步骤核对传入静态配置的资料版本及装备绑定；换装后由调用方重新请求 `account` 计算面板。静态面板与战斗效果使用一致的装备、套装件数和叠影。

当前实现依据：[`conversion.rs`](../../../core/account/src/playable/conversion.rs)按套装件数汇总 `set_properties`，按命途和叠影选择 `light_cones.properties`；[`panel.rs`](../../../core/account/src/playable/panel.rs)统一合成属性。新增战斗 JSON 沿用这些数据，避免另存一份静态倍率。

## 文件结构

| 字段 | 内容 |
| --- | --- |
| `schema_version` | 装备效果文件格式版本，与战斗场景格式分别管理 |
| `equipment` | `kind`、装备 ID；光锥的适用命途，套装的件数门槛按资料表达 |
| `provenance` | 游戏版本、资料版本、条目引用和核对状态 |
| `static_effects` | `account_reference`，关联 account 已有静态装备属性资料 |
| `battle_effects.parameters` | 战斗效果的固定值或叠影五档值，百分比使用比例值 |
| `battle_effects.modifiers` | 战斗状态：属性、共存组、层数、持续规则及清理规则 |
| `battle_effects.rules` | 按上下文计算的属性、光环或事件触发规则 |

战斗规则分成三类，静态效果沿用 account 现有实现：

| `type` | 用途 | 表中实例 |
| --- | --- | --- |
| `damage_modifier` | 在当前伤害上下文中判断条件并读取属性贡献 | 天倾、量子套四件、秘密誓心 |
| `aura` | 跟随条件、来源和受益对象变化而启停的持续贡献 | 龙骨、仙舟、隐士、游戏尘寰 |
| `trigger` | 事件发生时检查条件、次数与冷却，再执行有序效果 | 嘉果、猎人四件、轮契、舞！舞！舞！ |

入场初始化使用明确的入场事件触发。属性计算与事件执行分别处理，避免为了实时门槛判断反复添加、移除同一属性状态。

账号与战斗的联合样例核对每条贡献的计算归属，保证静态贡献只计入一次。

## 示例一：光锥五档参数与伤害范围

以下为光锥 `20002`「天倾」的拟议模板，倍率来自现有表。`damage_modifier`、参数引用与伤害标签读取属于待增加的能力，示例不是当前 CLI 输入。

```json
{
  "schema_version": 1,
  "equipment": {
    "kind": "light_cone",
    "id": "20002",
    "required_path": "Warrior"
  },
  "provenance": {
    "game_version": "4.7",
    "config_revision": "dfdfe3337bcfa14f000074d2dae7058118193ea6",
    "reference": { "category": "light_cone", "id": "20002" },
    "verification": "config_checked_game_pending"
  },
  "static_effects": {
    "type": "account_reference"
  },
  "battle_effects": {
    "parameters": {
      "damage_bonus": {
        "type": "by_superimposition",
        "values": [0.20, 0.25, 0.30, 0.35, 0.40]
      }
    },
    "modifiers": {},
    "rules": [
      {
        "id": "basic_skill_bonus",
        "type": "damage_modifier",
        "applies_to": {
          "actor": "wearer",
          "damage_tags_any": ["basic", "skill"]
        },
        "property": "damage_bonus",
        "value": { "op": "parameter", "key": "damage_bonus" }
      }
    ]
  }
}
```

本场绑定可以写成以下片段，其他角色字段沿用战斗场景：

```json
{
  "binding_id": "hero.light_cone",
  "kind": "light_cone",
  "equipment_id": "20002",
  "superimposition": 3
}
```

准备后该规则的值为 `{"op":"constant","value":0.30}`，来源带回穿戴者、绑定 ID、规则 ID 与叠影 3。原模板及准备后定义的摘要一起参与输入身份记录。五档参数在准备时统一替换，战斗效果中不再查询叠影。

伤害标签由具体技能和命中定义提供。追加攻击、附加伤害与持续伤害使用各自分类；不能只凭外层动作是战技就给内部所有伤害添加相同标签。

## 示例二：遗器触发与 buff

以下片段表示 `104`「密林卧雪的猎人」四件效果：终结技触发暴伤提高 25%，持续两回合。表中文字尚未确定精确触发阶段和倒计时规则，因此示例把待核对项写为 `unresolved`。模板可保存这些待核对项，正式准备入口遇到它们时返回具体缺项。

```json
{
  "equipment": {
    "kind": "relic_set",
    "id": "104"
  },
  "static_effects": {
    "type": "account_reference"
  },
  "battle_effects": {
    "parameters": {},
    "modifiers": {
      "ultimate_crit_damage": {
        "stack_group": "relic.104.4pc.crit_damage",
        "stacking": {
          "scope": "source",
          "update": "replace",
          "max_stacks": 1,
          "duration_refresh": "reset"
        },
        "duration": {
          "type": "turn_count",
          "count": 2,
          "clock": "holder",
          "tick_event": "unresolved",
          "turn_kinds": "unresolved",
          "first_tick": "unresolved"
        },
        "on_holder_death": "unresolved",
        "properties": [
          {
            "property": "crit_damage",
            "value": {
              "op": "constant",
              "value": 0.25
            }
          }
        ]
      }
    },
    "rules": [
      {
        "id": "4pc_ultimate_bonus",
        "type": "trigger",
        "requires": {
          "pieces": 4
        },
        "event": {
          "type": "action_used",
          "actor": "wearer",
          "action_kind": "ultimate",
          "phase": "unresolved"
        },
        "effects": [
          {
            "type": "add_modifier",
            "id": "ultimate_crit_damage",
            "stacks": {
              "op": "constant",
              "value": 1
            },
            "target": "self_unit"
          }
        ]
      }
    ]
  }
}
```

这里 `battle_effects.modifiers` 使用模板内局部 ID，准备步骤扩展为含装备及参数版本的定义 ID；`stack_group` 保留原身份。猎人二件的冰伤属性由静态引用关联 account 数据，四件规则在战斗中安装。穿戴者、装备绑定和规则 ID 合成完整来源。示例省略文件头与来源字段，完整文件按统一根结构保存。覆盖、叠层及死亡清理仍需与相应游戏规则一起核对。

## 条件、目标与触发次数

条件复用 `all`、`any`、`not` 与数值比较，增加明确的数据读取：单位当前/基础属性、HP 与能量比例、buff 层数与标签数量、实际弱点、队伍人数、命途/元素、站位、行动或命中记录。比较保持 `>`、`>=`、`==` 等原义。

读取时机分为准备时、入场时、实时属性查询和当前命中。诗人 `124` 的入场前速度门槛与格拉默 `311` 的战斗中速度门槛应使用不同读取时机。比例转换必须保留单位，`0.2%` 对应 `0.002`。

效果目标除现有自身、全体、随机敌人等选择器外，还需要：事件操作者、事件受击者、友方技能实际目标、实际受击集合、下一个行动的其他友方、符合条件的随机友方、特定站位、忆灵及所属角色。作用于召唤物时保留归属关系。

事件上下文增加 `turn_id`、`action_id`、`attack_id`、命中序号、双方身份、实际目标集合、暴击结果、原始/实际治疗、HP 损失及原因、护盾来源、能量/战技点变化及溢出。其中 Action、攻击、命中分别计数，技能效果文件不能用相同技能名称代替一次实际行动的身份。

触发限制用 `limit` 表达计数窗口和对象，用 `cooldown` 表达再次允许触发的时机。例如：每行动一次、每行动每目标一次、每回合一次、每波次一次、每场一次，及每三回合一次。次数重置、按技能种类首次、随机选择不重复、达到条件消耗层数都需要明确状态操作。现有 `uses` 仅表示总次数，无法代替这些窗口。

## 准备步骤与验收边界

1. 读取有版本的资料快照和装备绑定，核对 account 静态面板与本场装备的一致性，检查装备 ID、适用条件、套装门槛及参数范围；静态属性保留已有计算结果。
2. 对选中叠影取值，替换所有参数引用，保留参数来源；`by_superimposition` 必须有五项且等级在 1～5。
3. 展开 `battle_effects`，生成定义 ID、共存组与完整来源，检查引用、属性依赖、事件上下文和机制支持情况。
4. 生成固定参数的不可变输入、资料摘要与支持情况报告。未解决的计时或关键机制阻止该条目进入完整战斗模拟。
5. 每局独立创建状态。统一执行器响应事件、计算当前属性并更新状态；外部决策暂停时装备同样暂停。

叠影只选择已核对表值。模板值可以是不按等差排列的五档数值，转换时逐项选择；概率使用带类别的概率规则，例如基础概率 120% 保留 `1.2`，在具体命中流程中按规则处理。

JSON 结构检查负责字段类型和合法标记；语义检查负责参数、引用、机制、阶段和依赖。首批保持显式规则查找，遇到未实现机制返回装备、规则 ID 与 JSON 路径。资料导入可保存不完整条目及缺项报告，正式模拟默认要求本场选中的装备效果全部满足支持要求。

验收至少包含：五档参数逐一转换并回查原表；四件套只安装一次四件效果；跨叠影同类 buff 共存组一致；基础属性不重复计入；天倾只影响符合标签的命中；目标条件不会泄漏到其他目标；回合计时与一次性效果按已确认阶段处理；多段攻击按行动/攻击/目标窗口去重；随机效果显式使用随机流；同步与分步使用同一输入及操作得到同样结果。

建议按以下顺序补机制：

1. **模板准备与通用属性。** 五档转换、完整来源、属性基础分量、目标条件和命中范围，先接入嘉果、戍御、天倾等代表条目。
2. **事件、状态与资源。** 受击/击杀/暴击归因、计时、触发次数、消耗层数、动态属性、回能和战技点，接入猎人、拳王、轮契等。
3. **光环、状态分类与伤害扩展。** 目标查询、光环、概率/驱散、盾来源、治疗/耗血、附加伤害、持续伤害及击破规则。
4. **独立战斗系统。** 按角色与装备需求引入忆灵、召唤、欢愉及助战系统，再启用依赖它们的条目。

具体计时、触发阶段、非叠加效果多来源时的选取规则，以及货币战争前后台适用范围，按条目补来源证据。方案阶段保留这些缺项，不为原文中的“持续 N 回合”统一填写默认时点。
