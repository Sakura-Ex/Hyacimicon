# 装备效果 JSON 结构与机制覆盖方案

状态：设计草案，2026-11-18。装备读取、转换及执行扩展尚未实现。

本次对照[遗器套装效果](../../game-data/relic-set-effects.md)的 64 套、98 条效果及[光锥效果](../../game-data/light-cone-effects.md)的 172 件光锥整理机制需求。资料版本为 4.7，固定配置提交为 `dfdfe3337bcfa14f000074d2dae7058118193ea6`。代码对照版本为 `e961560`。

## JSON 只描述战斗效果

调用方传入 account 已组装的面板。静态加成沿用该面板，装备 JSON 只描述战斗需要执行的效果。版本和来源沿用资料快照，穿戴者、叠影和套装件数来自本场装备绑定。

文件保留装备 ID 与实际规则。用到状态时再定义状态，用到触发次数或持续时间时再填写对应规则。永久战斗 buff 仍属于战斗效果。

## 示例：天倾

光锥 `20002` 的普攻、战技增伤可以表达为：

```json
{
  "id": "20002",
  "rules": [
    {
      "type": "damage_modifier",
      "damage_tags": ["basic", "skill"],
      "property": "damage_bonus",
      "value": [0.20, 0.25, 0.30, 0.35, 0.40]
    }
  ]
}
```

`damage_tags` 匹配任一列出的命中标签。穿戴者由装备绑定提供。固定数值直接填写数字，五档叠影数值填写长度为 5 的数组；准备阶段根据叠影取值，例如叠影 3 转为 `"value": 0.30`。也可以导出五份固定参数定义，战斗只安装所选的一份，各档共用 Rust 类型和执行代码。

一个光锥可以有多条规则。伤害标签由技能与命中定义提供，附加伤害、持续伤害等按实际规则分类。

## 状态和触发按需要增加

三类战斗规则分别处理：

| 类型 | 用途 | 实例 |
| --- | --- | --- |
| `damage_modifier` | 当前命中的属性加成与目标条件 | 天倾、秘密誓心、量子套四件 |
| `aura` | 条件持续满足时影响指定对象 | 龙骨、仙舟 |
| `trigger` | 事件发生后检查条件并执行效果 | 嘉果、猎人四件、轮契 |

猎人四件需要终结技触发、暴伤状态和持续两回合；轮契需要能量效果及每回合次数限制。具体条目需要什么就定义什么，省略无用途的空对象。

buff 共存组与叠影数值分别表达，使不同叠影的同类效果仍遵循同一共存规则。装备来源、实例及计时设计见[生命周期方案](equipment-effects.md)。表中未明确的触发阶段、扣减时点和死亡保留规则留在核对记录中，确认后再加入可执行规则。

## 条件、目标与触发次数

条件复用 `all`、`any`、`not` 与数值比较，增加明确的数据读取：单位当前/基础属性、HP 与能量比例、buff 层数与标签数量、实际弱点、队伍人数、命途/元素、站位、行动或命中记录。比较保持 `>`、`>=`、`==` 等原义。

读取时机分为准备时、入场时、实时属性查询和当前命中。诗人 `124` 的入场前速度门槛与格拉默 `311` 的战斗中速度门槛应使用不同读取时机。比例转换必须保留单位，`0.2%` 对应 `0.002`。

效果目标除现有自身、全体、随机敌人等选择器外，还需要：事件操作者、事件受击者、友方技能实际目标、实际受击集合、下一个行动的其他友方、符合条件的随机友方、特定站位、忆灵及所属角色。作用于召唤物时保留归属关系。

事件上下文增加 `turn_id`、`action_id`、`attack_id`、命中序号、双方身份、实际目标集合、暴击结果、原始/实际治疗、HP 损失及原因、护盾来源、能量/战技点变化及溢出。其中 Action、攻击、命中分别计数，技能效果文件不能用相同技能名称代替一次实际行动的身份。

触发限制用 `limit` 表达计数窗口和对象，用 `cooldown` 表达再次允许触发的时机。例如：每行动一次、每行动每目标一次、每回合一次、每波次一次、每场一次，及每三回合一次。次数重置、按技能种类首次、随机选择不重复、达到条件消耗层数都需要明确状态操作。现有 `uses` 仅表示总次数，无法代替这些窗口。

## 准备步骤与验收边界

1. 使用传入面板、装备绑定与资料快照，检查装备 ID、适用条件、套装门槛及数值范围。
2. 按叠影把五档数组替换为选中数值；数组必须有五项且等级在 1～5。
3. 展开战斗规则，生成定义 ID、共存组与完整来源，检查引用、属性依赖、事件上下文和机制支持情况。
4. 生成固定参数的不可变输入、资料摘要与支持情况报告。未解决的计时或关键机制阻止该条目进入完整战斗模拟。
5. 每局独立创建状态。统一执行器响应事件、计算当前属性并更新状态；外部决策暂停时装备同样暂停。

叠影只选择已核对表值。模板值可以是不按等差排列的五档数值，转换时逐项选择；概率使用带类别的概率规则，例如基础概率 120% 保留 `1.2`，在具体命中流程中按规则处理。

JSON 结构检查负责字段类型和合法标记；语义检查负责参数、引用、机制、阶段和依赖。首批保持显式规则查找，遇到未实现机制返回装备、规则 ID 与 JSON 路径。资料导入可保存不完整条目及缺项报告，正式模拟默认要求本场选中的装备效果全部满足支持要求。

验收至少包含：五档参数逐一转换并回查原表；四件套只安装一次四件效果；跨叠影同类 buff 共存组一致；基础属性不重复计入；天倾只影响符合标签的命中；目标条件不会泄漏到其他目标；回合计时与一次性效果按已确认阶段处理；多段攻击按行动/攻击/目标窗口去重；随机效果显式使用随机流；同步与分步使用同一输入及操作得到同样结果。

建议按以下顺序补机制：

1. **模板准备与通用属性。** 五档转换、完整来源、属性基础分量、目标条件和命中范围，先接入嘉果、戍御、天倾等代表条目。
2. **事件、状态与资源。** 受击/击杀/暴击归因、计时、触发次数、消耗层数、动态属性、回能和战技点，接入猎人、拳王、轮契等。
3. **光环、状态分类与伤害扩展。** 目标查询、光环、概率/驱散、盾来源、治疗/耗血、附加伤害、持续伤害及击破规则。
4. **独立战斗系统。** 按角色与装备需求引入忆灵、召唤、欢愉及助战系统，再启用依赖它们的条目。

具体计时、触发阶段、非叠加效果多来源时的选取规则，以及货币战争前后台适用范围，按条目补来源证据。方案阶段保留这些缺项，不为原文中的“持续 N 回合”统一填写默认时点。
